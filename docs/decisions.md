# Design decisions

## 1. Grain: two fact tables

**Decision:** two facts with different grain.

- `fact_order_items`: one row is one order line (a product within an order). Key: `Order Item Id`. Measures: sales, quantity, discount, profit.
- `fact_orders`: one row is one order. Key: `Order Id`. Measures: shipping days (real, scheduled), delay.

**Why:** the source file has one row per order line. Amounts vary between
lines of the same order, while shipping data has a single value per order.
Keeping both in one table would repeat the delay once per line and distort
delay KPIs (e.g. an order with 3 lines counted 3 times).

**Evidence** (`src/explore_checks.py`):
- `Order Item Id` is unique (180,519 rows); `Order Id` has 65,752 distinct values.
- All shipping, date and location columns have one value per order.
- Amount columns differ between lines of the same order (45,902 orders with more than one line checked).

## 2. Columns excluded from the warehouse

**Decision:** 14 of the 53 source columns are not carried into the dw layer
(39 are kept). The staging table keeps all 53 columns as received.

**Duplicates** (identical to a column we keep):
- `Order Customer Id` = `Customer Id`
- `Order Item Cardprod Id` = `Product Card Id`
- `Product Category Id` = `Category Id`
- `Order Item Product Price` = `Product Price`
- `Sales per customer` = `Order Item Total`
- `Order Profit Per Order` = `Benefit per order`

**No information** (single value in all rows, or entirely empty):
- `Customer Email`
- `Customer Password`
- `Product Status`
- `Product Description`

**Mostly empty** (too sparse to analyse):
- `Order Zipcode` (86% empty; city, state, country and region are complete)

**Personal data** (not needed for any KPI; excluded to limit personal data in the warehouse):
- `Customer Fname`
- `Customer Lname`
- `Customer Street`

**Evidence** (`src/explore_checks.py`):
- Each duplicate pair: `!=` comparison returns 0 differing rows.
- Email, password, status: 1 distinct value. Description: 100% empty.
- `Order Zipcode`: 155,679 of 180,519 rows are empty.

## 3. KPIs

**Decision:** six KPIs, split by fact table.

Sales (from `fact_order_items`):
1. Total revenue: sum of `Order Item Total`.
2. Total profit and profit margin: sum of `Benefit per order`, divided by revenue.
3. Average order value: revenue divided by number of orders.

Shipping (from `fact_orders`):
4. Late delivery rate: late orders divided by orders that were not canceled.
5. Average delay in days: real minus scheduled shipping days, late orders only.
6. Number of orders.

**Why:** they cover both fact tables and the original goals of the project
(revenue and delivery delays). Each one can be sliced by the dimensions
defined in decision 4.

**Rules:**
- Canceled shipments are excluded from the delay KPIs, because no shipment took place and their day counts are meaningless.
- Delay is measured per order (in `fact_orders`), never per order line.

**Evidence** (`src/explore_checks.py`):
- `Late_delivery_risk` is 1 only when `Delivery Status` is "Late delivery", so it carries the same information.
- Real minus scheduled days is +1 to +4 for late orders, 0 for on time, and negative for early.
- For canceled shipments the difference ranges from -2 to +4, so it has no meaning.

**To verify in the cleaning phase:** 1,224 rows where `Sales` minus discount differs from `Order Item Total`.


## 4. Dimensions

**Decision:** six dimensions, each with its own generated key.

- `dim_customer`: customer id, segment, city, state, country, zipcode.
- `dim_product`: product id, name, price, image, category and department (id and name).
- `dim_date`: one row per day (year, quarter, month, day of week), generated by us.
- `dim_shipping_mode`: the 4 shipping modes.
- `dim_market`: market, region, country, state and city of delivery.
- `dim_order_status`: the 9 order statuses, with a flag `is_kpi_order` (0 for `CANCELED` and `SUSPECTED_FRAUD`, 1 for the rest).

**Facts:**
- `fact_order_items`: keys to product, customer, order date, market and order status; measures: quantity, sales, discount, discount rate, total, profit ratio, profit.
- `fact_orders`: keys to customer, order date, shipping mode, market and order status; plain columns: payment type, delivery status, late flag, shipping date; measures: real days, scheduled days, delay.

**Why:**
- Every KPI can be sliced by these dimensions.
- Category and department sit inside `dim_product`: each product has exactly one of each.
- Customers never change values, so no history is needed.
- Facts join only to dimensions, never to each other, so nothing is counted twice.
- Both facts point to `dim_order_status`, so every KPI applies the same rule without joining the facts.
- Only the order date links to `dim_date`; no KPI uses the shipping date.

**Note:** customer location and delivery location are different things.

**Evidence:** entity checks in `src/explore_checks.py` (customer, product and order columns have one value per key).

## 5. Layers

**Decision:** three layers in SQL Server: staging → clean → dw.

- `staging`: exact copy of the CSV, all 53 columns, as received. Loaded by Python.
- `clean`: fixes types (dates, numbers) and broken characters, drops the 14 excluded columns, calculates delay in days. Plain `.sql` files.
- `dw`: the five dimensions and two facts with generated keys. Plain `.sql` files.

**Why:**
- Each layer has one job, so errors are easy to locate.
- Staging stays an untouched copy of the source.
- Known data issues are handled in one place.

**Pipeline:** Python loads the CSV into staging, then runs the SQL files in order. Every run rebuilds all layers.

**Database:** SQL Server (local), connected to Power BI.


## 6. Source encoding

**Decision:** the CSV is read as `cp1252` (not `latin-1`). Characters missing from `cp1252` were replaced by `?` in the source file and cannot be recovered; they are left as they are.

**Evidence:**
- `Šiauliai` and `Žilina` loaded with an invisible first character under `latin-1` (codes 138 and 142); with `cp1252` they load correctly (codes 352 and 381).
- A literal `?` appears in 6 `Order State` and 6 `Order City` values (e.g. `Gy?r`, `Klaip?da`), in 309 rows (0.17%). No other text column is affected.


## 7. Country names

**Decision:** country names stay as in the source (Spanish, not translated). One change: `EE. UU.` in customer country becomes `Estados Unidos`, to match delivery country. `Puerto Rico` stays separate.

**Evidence:** customer country has 2 values (111,146 and 69,373 rows). Delivery country has 164 values and no country appears under two names. The United States is written `EE. UU.` in customer country and `Estados Unidos` in delivery country.

## 8. Customer zipcode

**Decision:** customer zipcode is kept as text and padded with zeros on the left to 5 characters. The 3 empty values stay `NULL`.

**Why:** the source stored the zipcode as a number, so leading zeros were lost (`725` instead of `00725`). All customers are in the US or Puerto Rico, where zipcodes have 5 digits.

**Evidence:** lengths in staging: 3 characters in 69,373 rows (all Puerto Rico), 4 in 6,135 rows, 5 in 105,008 rows, 3 empty.



## 9. Order status

**Decision:** all rows stay in the warehouse. `dim_order_status` has one row per order status and a flag `is_kpi_order`. Orders with status `CANCELED` and `SUSPECTED_FRAUD` (2,855 orders, 4.3%) have `is_kpi_order = 0` and are left out of all KPIs by filtering on this flag.

**Assumption:** these two statuses do not count as valid orders. This is a business rule, not a fact in the data. It lives in one place, so it can change without changing code.

**Revenue:** two figures. Gross revenue counts all orders; net revenue counts only orders with `is_kpi_order = 1`. The KPIs in decision 3 use net revenue.

**Why:** "Shipping canceled" appears only with these two statuses, so these orders have no real shipment. Both facts point to the same dimension, so revenue and delay KPIs use the same set of orders. In every other status about 57% of deliveries are late, so no further filtering is needed.

**Note:** statuses like `PENDING_PAYMENT` still carry a delivery result in the source; it is kept as it is.

**Evidence:** check 10 in `scripts/checks/staging_checks.sql` (crosstab of `Order Status` and `Delivery Status`, 65,752 orders).



## 10. Shifted customer columns

**Decision:** 3 rows (3 customers) have customer city, state and zipcode shifted by one position: the city is missing, `Customer State` holds the zipcode and `Customer City` holds the state code. In the clean layer, rows where `Customer State` is 5 digits are shifted back: state from the city column, zipcode from the state column, city set to `NULL`.

**Evidence:** check 13 in `scripts/checks/staging_checks.sql`. `Customer State` has 2-letter codes in all rows except 3 (`91732`, `95758`); in the same 3 rows `Customer City` is `CA` and `Customer Zipcode` is empty. Each of the 3 customers appears in one row only.
